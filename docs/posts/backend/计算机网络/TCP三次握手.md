# TCP 三次握手

## 一、握手要建立什么

TCP 是双向字节流，两个方向各有自己的初始序号。握手同步双方序号与相关连接参数，并确认双方能够在这条路径上发送和接收控制信息。

以下讨论客户端主动连接、服务端被动监听的常规过程，不覆盖同时打开和 TCP Fast Open 等扩展。

## 二、三步与状态变化

| 步骤 | 报文 | 关键内容 | 常见状态 |
| --- | --- | --- | --- |
| 1 | 客户端 SYN | `seq=x` | 客户端进入 SYN-SENT |
| 2 | 服务端 SYN + ACK | `seq=y, ack=x+1` | 服务端进入 SYN-RECEIVED |
| 3 | 客户端 ACK | `seq=x+1, ack=y+1` | 双方分别进入 ESTABLISHED |

SYN 占用一个序号，所以确认号要加一；纯 ACK 不额外占用序号。确认号表达下一段期望接收的字节序号，而不是报文编号。

## 三、为什么不能只做两次

收到第一步后，服务端知道客户端的初始序号；客户端收到第二步后，也知道服务端的初始序号。服务端还需要第三步确认自己的 SYN 被接收，避免把旧连接留下的延迟 SYN 直接当作已经建立的新连接。

“三次就是分别证明收发能力”可以辅助记忆，但完整回答应补上双向序号同步与旧报文防护。第三步并不一定是单独一包，可以与应用数据一起发送。

## 四、报文丢失与队列

第一步或第二步丢失时，相关端根据超时重传机制再次发送 SYN。第三步 ACK 丢失后，服务端可能重传 SYN + ACK，客户端收到后再次确认；若后续数据携带有效确认，也可能完成连接建立。

Linux 中常讨论保存未完成握手连接的 SYN 队列，以及等待应用 `accept` 的已完成连接队列。积压原因可能是连接攻击，也可能是应用来不及接收，不能只凭队列满就判断攻击。

## 五、面试简答与追问

**简答：** 三次握手同步双方初始序号，并让两端确认对方接收了自己的 SYN。第三次是服务端确认连接建立的重要环节。

**追问：握手完成说明服务器处理了请求吗？** 没有。建立传输连接、应用接受连接和业务处理是不同阶段。

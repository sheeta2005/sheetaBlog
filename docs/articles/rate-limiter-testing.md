# 用真实 Redis 验证限流：从阈值到故障策略

限流组件的结果依赖 Redis 脚本、时间边界、Spring 代理和自动配置。只验证 Java 返回值，容易漏掉脚本实际行为；只验证脚本，又会漏掉注解和配置是否真正接入。

我使用 JUnit 5、Spring 测试支持和 Testcontainers 分层覆盖这些问题。重点是每层测试说明了什么，以及测试结果属于哪一轮环境与版本。

## 四类测试对应四种问题

| 测试类 | 主要内容 | 为什么单独验证 |
| --- | --- | --- |
| RateLimiterAutoConfigurationTest | 条件装配、默认值、配置校验、异常分支 | 无 Redis 或禁用时应安全退出，非法配置应及时失败 |
| RateLimiterProxyTest | 接口代理及实现方法参数名 | 注解与表达式必须经过真实 Spring 代理 |
| RateLimiterIntegrationTest | 真实 Redis 下的双算法、窗口与键隔离 | 确认 Lua 与实际数据结构的行为 |
| RateLimiterRedisFailureTest | 连接后停止 Redis 容器 | 确认依赖中断时的放行与拒绝策略 |

当前源码包含 29 个测试方法：自动配置 14 个、代理 1 个、Redis 功能 13 个、真实故障 1 个。方法数量说明覆盖设计的规模，不等于某一轮实际成功执行数量。

## 阈值、恢复与隔离分别检查

阈值测试先使用一个固定业务键连续调用，检查前几次允许，达到配额后拒绝。固定窗口与滑动窗口分别执行，避免一个算法正常就替另一个算法背书。

恢复测试跨过窗口边界后再次调用，确认配额能够恢复。滑动窗口还检查只清除已经过期的记录，不能把仍在窗口中的请求一起删掉。

用户隔离测试使用不同业务参数，检查各自额度不相互占用；算法与窗口隔离则检查不同规则的键独立。SpEL 同时覆盖位置参数、对象属性和无效表达式回退，避免用户维度在接入后悄悄合并。

## 自动装配是功能的一部分

测试覆盖 Redis 模板存在与缺失、组件开启与关闭、业务自定义切面，以及默认 Redis 自动配置能否正确创建组件。

三级规则继承、非法全局值、脚本资源缺失和业务异常传播也需要检查。缺资源应在启动时失败，业务异常不能被故障放行吞掉，关闭组件后不能继续访问 Redis。

这些场景可以发现“引入依赖后应用启动失败”或“注解默认值覆盖全局配置”等接入问题，不能只靠算法用例覆盖。

## 真实故障先建立连接，再停止容器

故障用例在独立容器中启动 Redis，先证明正常调用可执行，再停止容器，分别观察 pass 与 deny 的结果。

如果只在启动前提供一个不可达地址，主要验证的是连接建立失败；先连接再停止能覆盖运行中依赖中断的路径。但单节点容器中断仍不能代表 Redis Cluster、主从切换或多节点网络分区都已经验证。

## “29 项通过”属于历史记录

简历记录过一轮 29 项用例全部通过。本次整理没有重新运行后端测试，而是核对现有用例与本地留存的 Surefire 报告。

留存报告显示自动配置 14 项、代理 1 项成功；两个 Redis 测试类因无法找到有效 Docker 环境而初始化失败，报告合计 17 项、2 个错误、0 个跳过。因此，不能把简历中的历史成绩当作这份报告或当前版本的全部通过证明。

需要复核时，应先准备可用 Docker，再在仓库根目录按 README 执行完整 Maven 验证，并保存同一轮生成的全部报告。当前集成测试不会因缺少 Docker 自动跳过，构建失败也应如实记录原因。

## 功能测试与容量测试分开

阈值、窗口和故障用例验证行为，不直接提供 RPS、P95 或多实例容量结论。容量需要另设请求模型、并发量、Redis 配置及持续时间，保存独立结果。

takeMe 当前使用自己的限流模块，其压测成绩不能直接算成这个独立 Starter 的性能证明。这样记录，才能让“做了哪些测试”和“已经验证哪些能力”对应起来。

# Redis 双窗口限流：固定窗口与滑动窗口的取舍

限流的规则可以是“每个对齐分钟最多允许多少次”，也可以是“任意连续 60 秒最多允许多少次”。这两种描述看起来接近，在窗口边界处却会产生不同的结果。

我的 Rate Limiter Starter 提供固定窗口与滑动窗口，业务方通过注解或全局配置选择算法。两种实现都在 Redis 中执行 Lua，应用实例共享相同业务键的状态。

## 固定窗口用 HASH 保存计数

脚本使用 Redis 服务端时间，按窗口秒数计算当前窗口编号。HASH 保存 `window` 和 `count`，窗口编号改变时重置计数，然后递增并与阈值比较。

**取得 Redis 时间 → 检查窗口编号 → 必要时重置 → 递增计数 → 返回允许或拒绝**。

首次计数设置到窗口边界附近的过期时间，并保留少量余量，用于清理不再使用的键。窗口切换由脚本中的编号判断完成，不能把过期删除视为唯一的重置机制。

当前固定窗口拒绝请求也会递增计数。它保存的是本窗口请求计数，不能把该数直接解释为业务方法已执行的次数。

## 窗口边界允许集中通过

假设规则为每分钟 5 次，用户在旧窗口最后一小段时间通过 5 次，又在新窗口开始后通过 5 次。两个窗口都遵守阈值，但很短的连续时间里通过了 10 次。

固定窗口适合状态量小、允许对齐时间段配额的场景。它无法单独保证任意连续时间段内都平滑，需要根据业务对突刺的容忍程度选择。

## 滑动窗口用 ZSET 保存通过请求

滑动窗口从 Redis TIME 取得秒和微秒，计算窗口左边界，清除边界及之前的记录，再检查剩余成员数量。

未超限时写入本次请求，分数为请求时间，成员使用 UUID，避免多个请求时间相近时互相覆盖。超限请求不写入，因此 ZSET 记录的是窗口内通过的请求。

窗口范围为 **(当前时间 − 窗口长度，当前时间]**。刚好位于左边界的记录已经过期，这个细节会影响临界时刻的判断与测试。

滑动窗口提供更连续的次数约束，但每次允许请求都会增加一个成员，内存占用随窗口内通过量增长；清理历史成员也有成本，不能只比较功能而忽略状态量。

## 为什么判断与写入放进同一个脚本

若应用先查询数量、再判断、最后写入，两个实例可能同时看到“还剩一个名额”，然后都执行写入。Lua 将清理、计数和阈值判断放在一次 Redis 执行中，避免这些步骤被其他请求穿插。

两种脚本都只访问传入的一个 Key，服务端时间避免了应用实例各自划分窗口时的时钟差异。Redis 服务端仍需要正常时间同步，脚本原子性也不能代替对故障、持久化和拓扑的独立评估。

## 键隔离与算法选择一起决定

当前 Key 包含业务前缀、算法、窗口秒数和业务维度。不同算法与不同窗口不会混用同一份状态；相同算法、窗口及业务键会共享额度。

阈值没有自动进入 Key。若两个接口使用同一业务键、相同窗口，但阈值不同，会操作同一份状态。因此共享额度时应统一规则，不共享时要增加接口或业务命名空间。

| 比较项 | 固定窗口 | 滑动窗口 |
| --- | --- | --- |
| 状态 | HASH 中的窗口编号与计数 | ZSET 中的通过请求 |
| 时间规则 | 对齐窗口 | 连续窗口 |
| 拒绝请求 | 计入当前计数 | 不新增成员 |
| 主要取舍 | 边界可能突刺，状态量较小 | 约束更连续，状态量与通过量相关 |

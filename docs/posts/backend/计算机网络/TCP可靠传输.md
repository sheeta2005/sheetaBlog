# TCP 可靠传输

## 一、可靠的是字节流

TCP 在连接可持续工作的条件下，为应用提供有序的字节流；发生不可恢复故障时会报告失败。它不承诺网络永远可用，也不保证业务操作只执行一次。

TCP 不保留应用消息边界。一次 `write` 可能分成多个段，多次写入也可能合并交付。应用应通过长度字段、分隔符或既定协议解析消息，“粘包”并不是 TCP 把业务消息弄坏了。

## 二、序号与确认

每个方向按字节编号。假设一段从序号 100 开始、包含 50 字节，接收方连续收到后会确认 150，表示下一步期望收到序号 150 的字节。

累计确认只确认没有缺口的连续范围。若中间一段丢失、后面的段已到达，确认号仍停在缺口处；支持 SACK 时可以额外告知已经收到的非连续范围，帮助发送方减少不必要重传。

## 三、重传与去重

| 机制 | 解决的问题 |
| --- | --- |
| 校验和 | 检测传输中的部分损坏，不能当作安全认证 |
| 超时重传 | 一段时间未获得所需确认时重新发送 |
| 快速重传 | 依据重复确认等信号较早判断丢包 |
| 接收端排序与去重 | 将乱序字节整理，并避免重复交付 |

经典快速重传以三个重复 ACK 为触发示例；具体实现也可能使用其他检测机制。重传计时根据 RTT 及其波动估计，过短会误重传，过长会拖慢故障恢复。

## 四、滑动窗口如何提高效率

逐段发送并等待确认会浪费链路时间。滑动窗口允许多个字节范围同时在途，确认前进后再继续发送。

可发送的数据量同时受接收方通告窗口和拥塞窗口约束，参见 [流量控制与拥塞控制](./TCP流量控制与拥塞控制)。只有不断增大 socket 缓冲区，不一定能提高业务吞吐。

## 五、面试简答与追问

**简答：** TCP 依靠字节序号、确认、重传和接收端重组提供有序传输；窗口允许流水线发送。连接失败仍需交给应用处理。

**追问：客户端超时后重试下单会重复吗？** 可能。服务端已执行而响应未到达时，TCP 无法替业务识别新请求是否重复，需要幂等键、唯一约束或事务状态查询。

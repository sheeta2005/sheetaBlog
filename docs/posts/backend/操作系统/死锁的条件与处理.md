# 死锁的条件与处理

## 一、四个必要条件

死锁是多个任务彼此等待对方持有的资源，无法继续推进。经典资源模型下需同时满足四个条件：

| 条件 | 含义 | 可采取的措施 |
| --- | --- | --- |
| 互斥 | 资源一次只能由一个任务持有 | 可共享资源改为共享访问 |
| 请求并保持 | 持有资源时继续等待其他资源 | 一次申请或失败后释放已有资源 |
| 不可剥夺 | 资源不能被强行安全取走 | 对可恢复资源设计撤销机制 |
| 循环等待 | 形成环形等待关系 | 全局统一加锁顺序 |

四条件是必要条件，不能只看到“用了两把锁”就断言一定死锁。多实例资源模型中的等待图判定也需要注意适用条件。

## 二、统一顺序的例子

转账线程如果分别先锁转出账户，就可能形成 A 等 B、B 等 A。按不可变、全局唯一的账户编号排序加锁，可消除环形等待：

```java
// 业务约束：账户编号唯一且不可变，所有双账户操作遵守同一加锁顺序。
Account first = from.id() < to.id() ? from : to;
Account second = from.id() < to.id() ? to : from;
synchronized (first) {
    synchronized (second) {
        // 在两把锁内校验余额并完成双方更新。
        transferBalance(from, to, amount);
    }
}
```

这是锁顺序示意，账户类型和余额校验由业务实现。数据库事务中的行锁也要尽量保持一致顺序，但数据库仍可能因其他访问路径发生死锁。

## 三、预防、避免、检测与恢复

**预防** 通过规则破坏必要条件；**避免** 根据未来最大资源需求，只批准不会进入不安全状态的分配，银行家算法属于此类。知道最大需求是前提，普通 Web 请求不容易满足。

**检测与恢复** 允许死锁发生，发现后终止或回滚某个参与者。数据库常选择一个事务回滚，调用方可以按业务幂等性和重试上限处理。

## 四、死锁、活锁与饥饿

死锁是相互等待而不推进；活锁是不断响应对方、反复重试却没有完成工作；饥饿是某个任务长期拿不到资源。无界立即重试可能把死锁风险变成活锁或负载风暴。

Java 平台线程的锁死锁可使用线程转储分析持有与等待关系。超时获取锁有助于恢复，但必须在失败路径释放已获得的锁。

## 五、面试简答与追问

**简答：** 死锁由互斥、请求保持、不可剥夺、循环等待共同构成。工程中优先统一锁顺序、缩短持锁区间，并设计失败释放和有限重试。

**追问：等待超时就解决死锁了吗？** 只有超时后真正中止等待并释放相关资源，才可能打破等待链；记录超时日志本身没有作用。

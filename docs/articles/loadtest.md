# 一次突发压测失败后的排查

takeMe 面向单小区业务。压测首先回答的是“当前实现能否在假设的常规与高峰流量下正确工作”，再观察突发时如何退化和恢复。

本文根据项目已有压测与优化文档整理，整理日期为 2026 年 10 月 5 日。

## 从人口假设到请求模型

测试使用 2500 名老人、250 名志愿者、25 名管理员的合成账号，部署为单 JVM、单 MySQL。注册人数不能直接换算成并发。

| 场景 | 虚拟用户数 | 目标 HTTP 请求速率 | 时长 |
| --- | ---: | ---: | ---: |
| 常规 | 60 | 30 RPS | 10 分钟 |
| 高峰 | 300 | 180 RPS | 10 分钟 |
| 突发 | 600 | 360 RPS | 10 分钟 |

JMeter 混合查询、建单、重试、模拟支付和取消操作，检查 HTTP 与 JSON 业务结果。推送连接另外统计，不能与 HTTP 虚拟用户相加成吞吐能力。

后端、JMeter、MySQL、Redis 和 RabbitMQ 共用一台 Windows 主机，约 15.7 GB 内存、16 个逻辑处理器。历史测试 JVM 使用 G1，初始堆 512 MB、最大堆 1024 MB。

## 失败具体表现在哪里

首次完整持续复测中，常规与高峰阶段没有业务错误；600 VU 突发阶段出现以下结果：

| 指标 | 突发阶段记录 |
| --- | ---: |
| 请求数 | 114108 |
| 失败请求 | 58 |
| 实际 HTTP RPS | 约 190 |
| P95 | 5464 ms |
| P99 | 6869 ms |
| Outbox 待发送采样峰值 | 1624 |
| 最老待发送事件年龄 | 226 秒 |

同时出现主机 CPU 采样达到 100%、内存余量降低、读超时和 JDBC 连接获取失败。只摘取较低错误率，会忽略秒级长尾和通知积压。

负载降回高峰后，恢复期仍有长尾，后续轮次 P99 恢复到 70 ms。这说明观察到了恢复能力，但不能把突发目标算作可靠容量。

## 为什么没有立即扩大 JVM 堆

将失败请求时间区间与 GC 日志对齐：历史记录中没有 Full GC 或 OOM，最大暂停为 71.075 ms，失败请求期间累计重叠暂停最大为 45 ms。

这些证据不足以解释数秒级请求失败，所以后续优先检查查库次数、锁等待、连接获取和通知积压。它不证明 GC 没有 CPU 或对象分配开销，也不证明所有失败只有一个根因。

## 下一步诊断与改动

独立诊断轮次使用 Arthas 观察调用和 SQL 次数，结合执行计划，发现列表 N+1 查询、看板重复统计及聚合扫描等问题。后续改为本页数据批量装配、调整索引与条件、合并统计，并补充并发冷回源合并。

**[具体改动与验证：从 N+1 查询到批量装配](./sql-optimization)**

## 短测改善与长期结论分开

后续两轮独立短对照使用相同社区参数，保留 600 条实际在线长连接，包含 60 秒预热和 180 秒突发。计分阶段没有 Maven 构建或 Arthas 增强同时运行。

| 指标 | 优化前短测 | 优化后短测 |
| --- | ---: | ---: |
| 实际 HTTP RPS | 241.21 | 330.06 |
| P95 | 3750 ms | 61 ms |
| P99 | 4908 ms | 221 ms |
| 错误数 | 0 | 0 |
| Outbox 待发送采样峰值 | 424 | 116 |

整体改动后的短测结果改善，但数据规模、缓存与 MySQL 缓冲状态仍有差异，主机还有其他程序运行。优化后没有再次完成一小时持续测试，因此原持续测试失败结果必须保留，不能用短测覆盖它。

后续应用初始堆目标调整为 1024 MB；旧测试数据不等于该新配置已通过验证。

## 可继续展开的讨论

- 目标 RPS 与实际 RPS 为什么不同？请求比例、思考时间和服务耗时怎样影响结果？
- 如何区分 JDBC 连接不足、慢查询与锁等待？目前缺少哪些时序数据？
- Outbox 积压代表发送延迟，还是已经丢消息？怎样验证最终落库和恢复？
- 同机短测能回答什么，独立环境与持续测试还需要验证什么？

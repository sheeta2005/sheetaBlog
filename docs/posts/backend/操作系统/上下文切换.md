# 上下文切换

## 一、切换的对象是什么

CPU 同一时刻只能在一个逻辑处理器上执行一个任务的指令。任务等待 IO、被抢占或主动让出 CPU 时，操作系统保存其执行现场，恢复另一个任务的现场，这就是上下文切换。

现场包括程序计数位置、寄存器、栈等必要状态。**保存上下文不等于复制全部堆内存**；进程的代码和数据仍保留在原地址空间中。

## 二、进程切换与线程切换

| 维度 | 同进程线程之间 | 不同进程之间 |
| --- | --- | --- |
| 寄存器、栈 | 需要切换 | 需要切换 |
| 用户地址空间 | 通常不变 | 通常需要切换映射上下文 |
| 缓存影响 | 数据访问不同也可能失效 | 还可能影响地址翻译缓存 |
| 隔离程度 | 共享进程资源 | 地址空间相互隔离 |

线程切换通常少一些地址空间相关工作，但成本不是固定的倍数关系。CPU 架构、缓存命中、跨核迁移和调度策略都会影响结果。

## 三、自愿与非自愿切换

**自愿切换** 通常来自任务无法继续执行，例如等待锁、IO 或条件变量。**非自愿切换** 通常来自调度抢占，例如 CPU 时间分配变化或其他任务需要运行。

两者都不是“主动调用线程 API 的次数”。一个请求等待数据库时，即使业务代码没有显式让出 CPU，底层阻塞也能造成自愿切换。

## 四、如何判断切换是否过多

Linux 可观察 `pidstat -w` 的进程级统计，结合 `vmstat` 的系统级 `cs` 指标。不同工具的统计范围和单位需要先确认，累计计数应比较一段时间内的增量。

若同时出现大量 runnable 线程、CPU 饱和和延迟上升，可检查线程池是否超过可利用的 CPU 并行度。若 CPU 不高、线程频繁等待，则应检查锁竞争与下游 IO，直接减线程可能进一步降低吞吐。

## 五、面试简答与追问

**简答：** 上下文切换让多个任务共享 CPU，需要保存恢复执行现场，并可能带来缓存和地址翻译开销。优化应先区分计算争抢与阻塞等待。

**追问：线程越多越快吗？** 不是。计算任务受 CPU 并行度限制；阻塞任务可以通过并发隐藏等待，但仍受连接池、内存和下游容量限制。参见 [线程和进程的区别](../Java基础相关/并发线程/线程基础/线程和进程的区别)。

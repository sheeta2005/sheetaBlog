# 头像上传不只涉及 OSS：文件校验与字段更新

头像上传看起来是“接收图片、存入 OSS、保存地址”。在 takeMe 中，它还关系到当前登录身份、可接受的文件范围，以及账号其他字段是否会在头像更新时被覆盖。

这部分实现让我把对象存储操作和数据库资料更新分开考虑：文件上传成功，不意味着整个业务过程已经完整成功。

## 从当前身份取得账号 ID

老人、志愿者和管理员分别通过对应接口管理头像。接口使用登录上下文中的账号 ID，读取上传文件，交给 OSS 工具上传，再由对应服务保存头像地址。

调用链为 **身份校验 → 取得上传内容 → 文件校验 → 上传 OSS → 更新头像字段 → 返回地址**。

服务端不根据上传请求中任意指定的用户 ID 更新资料。这与其他资料接口的字段白名单一起，避免把头像更新入口变成修改积分、账号状态或他人资料的入口。

## 文件名与大小先校验

当前 OSS 工具接受 `jpg`、`jpeg`、`png`、`gif`、`webp`，按配置限制文件大小。没有文件名、没有扩展名或不在允许范围内的后缀会被拒绝。

对象名由日期目录、角色目录和 UUID 组成，例如同一天上传的两个同名文件也会得到不同的对象键。用户原始文件名不直接作为最终路径，可以避免同名覆盖和将用户输入直接拼入对象路径。

扩展名校验并不等于图片内容校验。当前检查不能保证一个改名为 `.jpg` 的文件就确实是图片；内容解码、格式探测等应在需要时补充，不能把尚未实现的检查写进项目能力。

## 为什么只更新头像字段

读取账号实体后，另一条业务请求可能已经增加积分或改变状态。如果把第一次读到的整条实体重新写回，旧值可能覆盖另一条请求的结果。

当前头像服务按账号 ID 明确设置头像字段，只改变此次操作需要修改的数据。这样避免把先前读取的积分、状态等字段一起带回数据库。

删除头像同样明确设置 NULL。仅把实体字段赋为 null，可能被默认更新策略跳过，造成页面认为已删除、数据库却仍保存旧地址。

| 操作 | 数据库更新范围 | 需要避免的问题 |
| --- | --- | --- |
| 上传新头像 | 当前账号的头像地址 | 整条实体覆盖并发修改 |
| 删除头像 | 当前账号头像字段显式置空 | null 被更新策略忽略 |
| 其他资料修改 | 对应接口允许的字段 | 越权改变积分或账号状态 |

## OSS 与数据库没有共同事务

当前更新流程会处理旧头像对象，再保存新的头像地址。OSS 请求与数据库更新不在同一个本地事务里，因此存在上传成功但资料更新失败、旧对象处理与新地址保存不同步等窗口。

这说明“头像可以正常上传”与“已经具备完整的跨系统补偿”是不同结论。若继续完善，可评估新对象保存确认、旧对象延后清理和孤立对象回收；这些属于后续设计，当前文章不把它们描述为已经实现。

控制器当前会先读取文件内容，再由工具检查大小。请求层上传限制与内存占用需要一起评估，工具层的大小判断不能直接等同于接收层已经限制了全部资源消耗。

## 验证要覆盖并发资料变更

已有资料安全与数据库测试关注：头像更新不覆盖积分、删除后字段确实为空，以及资料接口的可编辑范围。OSS 在相关回归中使用测试替身，测试结果不能证明真实对象存储在网络故障下的完整恢复行为。

本文最关注的是更新范围：一个看似很小的头像功能，也需要避免把其他业务数据写回旧值。

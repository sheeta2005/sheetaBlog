# 从重复下单到并发接单：订单约束怎么落到数据库

takeMe 的订单包含多个服务项。老人可能因为网络重试重复提交，志愿者可能同时抢同一个服务项，同一志愿者也可能连续点击两个服务。取消与开始服务还会互相竞争。把按钮置灰能改善交互，最终约束仍要落到服务端和数据库。

我把这些问题分成两类：重复提交要返回同一个业务结果，并发状态变化要确保只有符合条件的操作成功。

## 重试沿用同一个 requestId

创建订单时，客户端为一次预约内容生成 `requestId`。请求失败后重试沿用这个标识；预约内容改变后，才生成新标识。后端校验标识格式，数据库以 `(user_id, request_id)` 建立联合唯一约束。

事务先锁定老人账号，再以当前读查询该账号的提交标识。已有订单就返回原结果，首次提交才创建订单和服务项。同一请求的两个线程因此不会各自完成一套建单流程，唯一索引同时承担最终的重复约束。

这里的幂等键包含用户 ID，不同老人可以使用相同的提交标识。服务价格、订单归属和初始状态由服务端确定，不能从客户端直接照搬。购物车结算也复用这套思路，重试返回旧订单时不应清理后来新加入的服务。

## 两种接单竞争需要不同的锁

| 竞争场景 | 要保护的业务约束 | 当前处理 |
| --- | --- | --- |
| 同一个人同时抢两个服务项 | 志愿者不能同时持有多项活动服务 | 先锁志愿者账号，再检查活动服务 |
| 两个人抢同一个服务项 | 一个服务项只能被一个人接取 | 锁父订单及服务项，再检查状态与接单者 |
| 取消与开始服务同时发生 | 已开始服务不能被旧状态取消 | 当前读复核状态，按前置状态条件更新 |

单独锁服务项解决不了“同一个人抢不同服务项”。两个请求访问不同的行，仍可能各自认为志愿者没有活动服务。因此需要先按志愿者账号串行化，再读取活动服务情况。

接单采用读已提交隔离级别，并固定为 **志愿者账号 → 父订单 → 服务项** 的加锁顺序。活动项查询不提前持有服务项锁，避免与其他流程形成相反的锁等待关系。

## 读到状态，还要按状态更新

接单之前，以当前读获取锁定后的记录，检查订单是否可接、服务项是否待接、接单者是否为空，以及账号状态、积分和预约时间。

最终更新仍包含“服务项为待接状态且接单者为空”的条件。只有影响行数为 1 才视为成功；否则按业务冲突处理。状态转换也检查旧状态，条件更新失败会抛出异常并回滚。

取消或放弃服务时，接单者字段需要明确写成 NULL。仅给实体字段赋 null 可能被 ORM 的更新策略忽略，因此该流程使用显式更新，避免状态已取消但接单者仍残留。

## 为什么统一顺序比再加一把锁更有用

两个事务分别持有不同的锁，再请求对方持有的锁，就可能形成死锁。项目材料记录过一次实际竞争中的死锁，修正了接单的锁顺序，并增加 20 次重复竞争回归。

这次处理关注整条业务路径持锁的顺序，也关注活动项查询带来的锁范围。读已提交是与具体查询一起使用的选择；仅修改隔离级别，不能保证任意业务都不会死锁。

## 验证关注最终业务结果

测试分别构造同人抢多项、多人抢同项，以及取消与开始服务的竞争，检查成功数量、服务项归属、父订单汇总状态和数据库最终记录。幂等建单则检查重复请求返回同一订单，修改后的预约使用新标识。

这些约束依赖同一 MySQL 的事务、行锁和唯一索引。当前项目按单 JVM、单数据库部署，尚未以多节点业务压测证明跨实例的完整行为；模拟支付与退款也不代表真实支付平台的幂等方案。

# 性能参数与故障排查

## 一、先给请求链路定预算

入口代理、Tomcat、业务调用和数据库各有不同超时。连接建立、等待首个请求、keep-alive 空闲以及异步请求完成，也不是同一种计时。

应让下游调用有合理期限并留出失败处理时间。Tomcat 的 `connectionTimeout` 不是“控制器运行超过这个时间就自动停止”，同步业务取消需要应用与客户端机制配合。

## 二、容量与参数的边界

| 关注点 | 参数或指标 | 验证方法 |
| --- | --- | --- |
| 工作并发 | maxThreads、忙线程、任务等待 | 对齐负载和下游池容量 |
| 连接容量 | maxConnections、acceptCount | 观察连接状态与系统积压 |
| 空闲复用 | keepAliveTimeout、maxKeepAliveRequests | 比较握手成本与空闲资源 |
| 请求约束 | 头部、参数、特定表单解析限制 | 用目标请求类型验证 |
| JVM 资源 | 堆、元空间、栈、直接内存 | 比较 RSS、GC 与线程数量 |

`maxPostSize` 针对特定表单参数解析，不应当作所有请求体的通用大小限制。请求头相关参数也应按目标 Tomcat 版本核对。

## 三、四种症状的排查路径

**CPU 高：** 先确认是业务线程、GC 还是系统开销，再取得线程转储与 CPU 采样，检查热点、死循环和锁竞争。

**请求慢而 CPU 不高：** 查看工作线程是否等待 SQL、连接池、远程调用或锁。反复增加 Tomcat 线程可能加剧下游拥塞。

**连接持续增长：** 区分 ESTABLISHED、TIME_WAIT 与 CLOSE_WAIT，核对 keep-alive、客户端行为和关闭路径，不能把所有连接直接当作泄漏。

**内存增长：** 观察回收后存活量、线程数、类加载器和直接内存。RSS 超过堆大小很正常，但持续超出预算需要分项定位。

## 四、采集证据再验证调整

```shell
# JDK 21：用真实目标 PID 采集线程现场，重复间隔应结合故障持续时间。
jcmd 12345 Thread.print -l
# 查看启动参数，确认改动实际生效。
jcmd 12345 VM.command_line
```

访问日志记录状态和耗时，JMX 观察连接器、线程池与 JVM，再与应用链路日志关联。只根据一次快照无法区分持续卡住与正常瞬时等待。

调整后用同样请求量验证吞吐、P99、错误率和资源消耗。并发增加但错误和超时更多，不能称为性能提升。

## 五、面试简答与追问

**简答：** Tomcat 调优先定位网络、线程、下游和 JVM 中的瓶颈，再修改相应容量或期限；配置必须验证生效，结果以业务指标判断。

**追问：重启恢复就证明线程池配置错了吗？** 不能。重启同时清除了连接、缓存、线程与临时状态，只能作为现象，需要保留故障证据继续定位。

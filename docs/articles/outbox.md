# 订单通知为什么使用 Outbox

takeMe 的订单变更会触发跨角色通知。需要处理的具体问题是：数据库和消息代理是两个系统，不能靠一次普通方法调用保证它们同时成功。

本文依据截至 2026 年 10 月 5 日的本地业务设计与发送任务实现整理。

## 直接发送会留下什么窗口

若业务先提交数据库，再发送通知，提交后进程退出或 Broker 不可用，订单已经改变，通知却没有可靠的待处理记录。

若先发送再提交，通知可能被消费，但业务事务最终回滚。在数据库事务中等待 Broker 确认，还会把网络等待引入业务事务。

## 把业务变更和待发送事件一起保存

当前实现将订单变更与 Outbox 事件保存在同一个数据库事务中。事务回滚，两者一起回滚；事务提交后，即使暂时无法发送消息，数据库中仍保留待发送事件。

**业务事务：校验与状态变更 → 写入 Outbox → 提交**

**后台投递：查询到期事件 → 发送并等待确认 → 更新发送状态**

业务请求不等待 Broker 确认。后台任务约每秒扫描一次到期事件，逐条在独立事务中加锁处理。

## 确认成功后才标记已发送

发送任务恢复事件类型与载荷，携带原事件 ID 调用确认发送。只有确认成功且未被退回，才将事件标记为已发送。

失败时保留待处理状态，记录错误与尝试次数，根据尝试次数增加下一次等待时间，最长等待 300 秒。此处失败记录是恢复依据，而非仅供查看的业务日志。

关闭 MQ 时保留 Outbox 记录，恢复启用后继续投递。

## 为什么仍然可能重复

消息发送成功后，如果应用在保存“已发送”状态前退出，下一轮会再次发送同一事件。因此接收方仍然需要幂等处理。

takeMe 的通知消费端保留事件 ID，消息表使用数据库唯一约束防止重复插入，重投不重置已读状态。在线推送发生在消息持久化后，离线用户仍能从数据库查询通知。

这套设计不等于端到端 Exactly Once。WebSocket 临时提醒仍可能因重投重复出现，最终消息表去重与客户端显示去重是不同问题。

## 失败场景与预期行为

| 场景 | 当前设计的预期行为 |
| --- | --- |
| 业务事务回滚 | 订单变更与 Outbox 一起回滚 |
| Broker 暂时不可用 | 事件保留，后台按计划重试 |
| 发送成功、状态保存前退出 | 可能重投，消费端依靠事件 ID 去重 |
| 用户离线 | 消息已持久化，后续查询；不依赖唯一一次在线推送 |
| 消费速度不足 | 观察队列和 Outbox 积压，不能只看 HTTP 延迟 |

上述表格描述设计行为，不代表每个进程退出和网络故障场景都已完成真实演练。

## 容量和一致性的取舍

当前单次扫描数量有限，且逐条同步等待发送确认。突发流量下扫描频率与确认耗时可能影响发送吞吐；Outbox 行锁也会持续到发送结果保存。

因此除了最终是否发送，还需要观察待发送数量、最老事件年龄、队列 ready / unacked 和恢复时间。首次持续压测曾出现待发送采样峰值 1624、最老事件 226 秒；不能据此直接认定丢消息，也不能把积压忽略。

系统未验证跨数据库、多地域一致性、全链路顺序或任意规模的通知吞吐。扩展容量需要新的测量和设计，不应从当前单 JVM 结果直接外推。

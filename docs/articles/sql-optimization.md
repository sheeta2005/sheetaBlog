# 从 N+1 查询到批量装配

takeMe 的性能排查先从可观测的查询行为入手：一个列表请求究竟执行多少次 SQL，哪些查询重复，哪些条件妨碍索引访问，以及冷缓存时是否有多个线程重复回源。

本文整理自 2026 年 10 月 5 日的 SQL、GC 与 Redis 专项复盘。

## 列表为什么会产生 N+1

老人订单列表先查询主列表，再对每条订单查询服务项。一页 10 条记录时，COUNT、主列表与 10 次服务项查询合计 12 次业务查询。

志愿者待接列表还逐条查询父订单和老人信息，一页 10 条时达到 22 次业务查询。数据装配看起来只是循环，实际放大了数据库往返和对象创建。

## 只围绕本页数据批量装配

老人列表先取得本页订单 ID，再批量查询服务项并按订单 ID 归组。志愿者列表分别收集本页父订单和老人 ID，各做一次批量查询，再装配结果。

改动保留分页和原有返回语义，不读取全部历史订单来拼装当前页。空页、关联缺失、稳定排序和非法分页参数也分别验证。

| 一页 10 条记录 | 优化前业务查询 | 优化后业务查询 | 含鉴权的完整请求 |
| --- | ---: | ---: | --- |
| 老人订单列表 | 12 | 3 | 13 → 4 |
| 志愿者待接列表 | 22 | 4 | 23 → 5 |

查询次数来自 Arthas 诊断记录，不是接口延迟分位数。

## 看板、时间条件与索引

| 问题 | 改动 | 验证重点 |
| --- | --- | --- |
| 看板重复做多次订单 COUNT | 合并为条件聚合 | 状态统计与当日时间上下界 |
| 收款、退款用 OR 跨两种时间字段 | 两类独立聚合后相减，补覆盖索引 | 保持模拟净收款口径 |
| 日期与时间 CONCAT 筛选 | 使用日期范围及时间上下界 | 跨午夜与候选筛选的执行计划 |
| 同秒记录排序不稳定 | 按创建时间与 ID 排序 | 相同时间记录的分页结果 |
| 负数页大小绕过分页 | 限制页大小为 1～100 | -1、0、101 的真实 HTTP 请求返回 400 |

执行计划和单次方法耗时用于诊断访问路径，不能代替接口 P95，也不能单凭一次缓存命中认定 SQL 优化收益。

## 冷缓存并发回源

缓存 miss 后，在单 JVM 内按固定的 64 条锁条带合并回源：获取锁后再次检查缓存，已有结果就复用，否则执行查询并写入缓存。

目录修改后的主动失效与回源写入共用同一锁，避免旧查询在失效之后重新写入旧目录。锁数量固定，防止按无限陌生键创建锁对象。

目录和看板 TTL 增加约 ±10% 抖动。有限的目录类型先做参数校验；空列表可以缓存，null 使用短期哨兵。查询缓存异常时回源数据库，业务数据库异常继续向上抛出。

诊断记录中，冷看板同时发起 20 个真实 HTTP 请求，全部成功，观察到代理调用 20 次、实际业务回源 1 次。这是单 JVM 的一次验证，不代表多实例缓存一致性或 Redis 整体宕机容量。

## 测试与短测结果

已有记录显示：先补充边界和并发测试，原实现出现 3 个失败、2 个错误；改动后全量回归 111 项中，90 项成功、21 项既有演示跳过，失败为 0。索引二次修正后，73 项相关专项测试再次通过。

独立性能对照保留相同社区参数与 600 条实际在线长连接，两轮均为 60 秒预热、180 秒突发：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 实际 HTTP RPS | 241.21 | 330.06 |
| P95 | 3750 ms | 61 ms |
| P99 | 4908 ms | 221 ms |
| 错误数 | 0 | 0 |
| 进程工作集采样峰值 | 928.84 MB | 954.38 MB |

保留工作集略升等反向指标。改善属于整体改动前后观测，不能全部归因于某个索引；两轮数据和缓存状态也不是严格相同。优化后尚未完成一小时持续复测。

## 仍然存在的边界

- 锁条带合并回源仅适用于当前单 JVM，多节点需重新设计协调方式。
- 历史短压测 Redis 为 64 MB、noeviction；正式目标配置为 allkeys-lru，两者不能混用测试结论。
- 普通缓存和限流计数共享 Redis 时，淘汰可能影响配额，严格限流需单独评估。
- Redis 全实例故障、内存上限、多 JVM 协调和超深分页尚未完成对应实测。

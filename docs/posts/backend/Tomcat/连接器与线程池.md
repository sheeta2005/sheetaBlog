# 连接器与线程池

## 一、连接数不等于工作线程数

NIO 连接器可维护许多连接，只把需要处理的活动交给工作线程。keep-alive 空闲连接、正在读取的连接和执行应用的请求，是不同资源状态。

因此不能把“最大连接数”理解为服务器同时运行同样数量的 Servlet，也不能认为每条连接永远绑定一条业务线程。

## 二、关键参数

| 参数 | 主要作用 | 容易混淆的点 |
| --- | --- | --- |
| `maxThreads` | 内部工作线程池上限 | 不是最大 socket 数 |
| `minSpareThreads` | 内部线程池维持的最少线程数 | 不是当前必须空闲的线程数 |
| `maxConnections` | 连接器接收并处理的连接数量上限 | 包括不正在执行业务的连接 |
| `acceptCount` | 达到连接接收上限时的系统连接积压设置 | 不是 Java 业务任务队列长度 |
| `connectionTimeout` | 指定连接阶段的等待超时 | 不是统一的业务执行期限 |

实际积压队列还受操作系统限制影响。HTTP/2 并发流等协议也有额外配置，不能只看这一张表推导所有连接行为。

## 三、使用共享 Executor

```xml
<!-- 独立 Tomcat 10.1 示例：线程配置放到被 Connector 引用的 Executor。 -->
<Executor name="webThreads" namePrefix="web-"
          maxThreads="120" minSpareThreads="12" />
<Connector port="8080" protocol="org.apache.coyote.http11.Http11NioProtocol"
           executor="webThreads" maxConnections="2048" acceptCount="100"
           connectionTimeout="20000" />
```

这些容量是演示值。配置外部 Executor 后，Connector 的内部线程池参数不再负责对应的池，应在 Executor 上调整，避免“改了 maxThreads 却没有变化”。

## 四、从负载估计并发

稳定系统中可用 Little 定律估算：在途请求数量约为到达率乘平均停留时间。100 次每秒、平均耗时 0.2 秒，对应约 20 个在途请求。

这不直接等于最终线程池大小，因为异步、排队、长尾与峰值会改变需求。还要核对数据库连接池、外部服务容量和 CPU；增加工作线程可能只是制造更多下游等待。

## 五、面试简答与追问

**简答：** Connector 维护协议和连接，工作线程执行请求。连接上限、系统积压和线程池容量各司其职，使用共享 Executor 时在执行器上配置线程。

**追问：线程池满为什么延迟上升？** 任务可能排队，或连接接收受限；队列过长会放大尾延迟。应结合忙线程数、队列、超时和下游等待定位。

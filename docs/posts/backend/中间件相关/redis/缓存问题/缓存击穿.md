# 缓存击穿

## 一、定义与相邻问题

热点数据缓存失效时，大量并发请求同时回源数据库，可能瞬间放大数据库压力。触发原因不只是自然过期，还包括淘汰、删除、重启后冷缓存等。

| 问题 | 典型原因 | 主要应对方向 |
| --- | --- | --- |
| 击穿 | 单个热点失效，同时回源 | 合并重建、互斥、提前刷新 |
| 穿透 | 查询不存在的数据 | 空值缓存、过滤与输入约束 |
| 雪崩 | 大量缓存集中失效或服务故障 | 分散失效、容量保护与降级 |

实际故障可能同时包含多种情况，不能只根据“数据库压力大”确定名称。

## 二、互斥重建与二次检查

缓存未命中后，仅让获得重建资格的请求回源；其余请求进行有上限的等待、重试或降级。获得锁后 **再次检查缓存**，因为其他请求可能已经完成重建。

```text
读取缓存
  → 命中：返回
  → 未命中：尝试获得该 key 的重建锁
     → 获得：二次读缓存；仍无值才查库、写缓存；最终释放自己的锁
     → 未获得：有限等待并重读，或返回约定降级结果
```

单进程锁只能协调当前实例，多实例需要跨实例机制。分布式锁应有唯一持有标识、合理租期和验证持有者后释放的原子操作，避免误删别人的锁。

锁租期过短可能出现旧持有者未完成而新持有者开始重建。续期、失败处理和写入版本策略需要按业务验证，不能声称“用了 Redisson 就无条件保证所有场景正确”。

## 三、互斥不等于强一致性

重建锁主要控制并发回源，不自动让数据库更新与缓存写入变成原子事务。仍可能发生旧查询结果覆盖新缓存、删除与重建交错等情况。

是否需要版本校验、更新事件或其他一致性设计，取决于读写语义。应清楚说明允许的陈旧时间，而不是只写“一致性强”。

## 四、逻辑过期与提前刷新

逻辑过期把有效期放在缓存值中：未到期直接返回；到期时用受控执行器异步重建，并按约定返回旧值。它用短期陈旧换取更平稳的回源压力。

需预热或处理首次无值，限制重建并发和队列，约定刷新失败后的最大陈旧窗口。缓存物理丢失时没有旧值可返回，必须回到未命中保护流程。

不设置物理 TTL 只能避免自然过期，仍会面对淘汰、冷启动与人工删除。定时刷新也需处理失败，不能说“彻底杜绝击穿”。

## 五、随机 TTL 的适用范围

随机 TTL 主要打散多个 key 的集中失效，有助于缓解雪崩。单个热点 key 在某一时刻失效时，并发仍可能同时回源，随机偏移本身没有合并这些请求。

热点场景可结合提前刷新、互斥重建、缓存预热与数据库容量保护。具体选择要看是否能返回旧数据及接口期限。

## 六、面试简答与追问

**简答：** 击穿是热点失效后的并发回源。互斥重建要二次检查并有限等待，逻辑过期要有旧值和失败策略；永久 TTL 与随机 TTL 都不是单热点的完整保护。

**追问：锁失败可以无限递归重试吗？** 不应这样做。它会增加线程、栈和负载压力，应有等待上限、请求期限和可解释的降级结果。

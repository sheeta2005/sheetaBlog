# HTTPS 与 TLS 握手

## 一、TLS 提供什么

HTTPS 使用 TLS 保护 HTTP 通信，目标包括机密性、完整性与对端身份验证。常规网站主要验证服务器身份；双向 TLS 还可以验证客户端证书。

证书绑定公钥与身份信息，并由可信体系签名。证书不会自动证明业务接口有权限控制，也不能防止服务器自身的 SQL 注入或错误授权。

## 二、TLS 1.3 的简化流程

1. 客户端发送 ClientHello，提供协议能力、随机数和密钥交换参数等。
2. 服务端发送 ServerHello，选择参数，双方据此计算握手所需密钥。
3. 服务端发送加密的后续握手信息、证书、签名证明与 Finished。
4. 客户端验证证书链、目标名称、有效期及签名等，检查 Finished，再发送自己的 Finished。
5. 双方使用协商派生的应用流量密钥加密传输。

这是典型的证书握手概述，预共享密钥恢复、客户端认证和 HelloRetryRequest 会改变细节。不要把 TLS 1.2 的 RSA 密钥传输流程当成 TLS 1.3 的通用流程。

## 三、非对称与对称算法的分工

非对称机制用于身份签名验证和相应的密钥协商；对称认证加密用于大量应用数据传输。证书公钥通常不是直接逐字节加密整个网页的工具。

典型的临时 Diffie-Hellman 密钥交换可以提供前向保密：以后长期签名私钥泄漏，也不应直接恢复此前已结束会话的流量密钥。不能把所有恢复模式都无条件概括为完全相同的保证。

## 四、会话恢复与 0-RTT

会话恢复减少完整验证和协商成本。TLS 1.3 的 0-RTT 可让满足条件的客户端较早发送应用数据，但这些早期数据具有重放风险，安全属性与普通握手后的数据不同。

支付、下单等操作不能只因“已经加密”就默认适合 0-RTT。应在协议和应用层共同约束可使用的请求，必要时拒绝早期数据。

## 五、面试简答与追问

**简答：** TLS 握手验证身份并协商密钥，再以对称认证加密保护通信。证书验证、握手版本与会话恢复的安全边界都要分清。

**追问：HTTPS 会隐藏所有访问痕迹吗？** 不会。网络仍可能观察地址、连接时序与流量大小；DNS、SNI 等可见性取决于具体部署和扩展，不能直接承诺完全匿名。

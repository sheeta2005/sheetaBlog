# 常见垃圾回收器

## 一、先区分并行与并发

**并行** 是多个 GC 线程一起工作；**并发** 是 GC 的部分工作与应用同时进行。并行收集器仍可以暂停应用，并发收集器也通常存在暂停阶段。

本文区分历史 JDK 8 组合与 JDK 21 实践，不能把不同年代的参数和默认行为放在同一个运行环境中。

## 二、Serial 与 Parallel

Serial 以较简单的串行回收工作为特点，适合重点关注资源开销的小型负载；Parallel 使用多个 GC 线程处理回收，主要追求吞吐，回收时仍有 STW。

JDK 8 常见服务端默认组合是 **Parallel Scavenge + Parallel Old**，不是 ParNew + Parallel Old。ParNew 是历史上与 CMS 配合的年轻代收集器。

| 收集器 | 主要倾向 | 需要考虑 |
| --- | --- | --- |
| Serial | 较低管理开销 | 大堆或严格延迟场景中的暂停 |
| Parallel | 吞吐与并行回收 | 业务对长暂停的容忍程度 |
| G1 | 吞吐与暂停目标平衡 | Region、分配余量与软暂停目标 |
| ZGC | 更低的 GC 暂停影响 | 并发 CPU 开销、内存余量与版本 |

不应只凭“互联网服务”或“堆大小”直接得出固定选择。

## 三、CMS 的历史位置

CMS 针对老年代，经典过程包括初始标记、并发标记、重新标记与并发清理。它减少部分长暂停，但仍有 STW，并需要面对浮动垃圾、碎片和并发失败等问题。

CMS 在 **JDK 9 被弃用、JDK 14 被移除**。它适合解释旧系统与面试历史知识，不是 JDK 21 的可选生产参数。标记阶段结束不保证回收所有刚刚失去引用的对象。

## 四、G1 与 ZGC

G1 虽然不要求年轻、老年代物理连续，仍保留分代概念，通过 Young 与 Mixed 回收处理不同 Region。疏散复制有助于整理空间，但大对象仍有特殊路径。

ZGC 把更多工作并发化以降低暂停。JDK 21 的分代实现需要 `UseZGC` 与 `ZGenerational`；后续版本默认与支持范围发生变化，应查对应版本。

详细取舍见 [G1 与 ZGC 如何选型](./G1与ZGC如何选型)。这里不把“低暂停”误写成“业务完全无停顿”。

## 五、选型验证

先给出业务延迟、吞吐与资源目标，在相同 JDK、硬件、堆预算和数据负载下比较。GC 停顿降低但 CPU 竞争导致请求 P99 上升，不能只依据 GC 数值宣布改进。

还要记录启动预热与持续运行表现，避免用一次短压测替代稳定性验证。

## 六、面试简答与追问

**简答：** Serial 偏简单，Parallel 偏吞吐，G1 兼顾暂停与吞吐，ZGC 重点降低暂停；CMS 属于已移除的历史方案。并行与并发不同，选择取决于版本和可验证目标。

**追问：并发回收就不需要暂停吗？** 不是。部分协调与安全处理仍需暂停，且并发工作会与业务竞争资源。

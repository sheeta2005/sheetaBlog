# 类卸载与类加载器泄漏

## 一、类为什么也有生命周期

动态代理、插件与应用热部署会加载新的类。类元数据持续增长时，需要关注这些类及其加载器能否被回收，而不只是堆中的普通业务对象。

Java 规范允许类在其 **定义类加载器可被回收** 时卸载；由引导类加载器加载的类不按这种条件卸载。是否及时执行卸载，还取决于虚拟机、收集器与相关设置。

## 二、理解加载器可达性

“这个类没有实例”不是充分条件。类对象、实例、线程上下文类加载器或其他引用仍可能使相关加载器可达。不要把卸载说成遍历发现“没调用过的方法”就立即删除类。

判断时先寻找从 GC Roots 到加载器的强引用链。只有相关生命周期关系允许释放，才可能回收对应元数据；不同对象的可达性需要结合虚拟机处理理解，不能只看一个局部变量是否赋为 null。

## 三、典型的热部署泄漏链

应用卸载后，一个仍运行的后台线程可能继续持有旧 Web 应用加载器：

`存活线程 → contextClassLoader → 旧 WebappClassLoader → 旧应用类与静态数据`

类似问题也可能来自长寿命线程上的 ThreadLocal、父加载器中的缓存、没有注销的驱动或监听器。把静态字段设为 null 只处理一条引用，不能自动清除整个外部引用链。

## 四、如何诊断与修复

```shell
# JDK 21：观察类加载和卸载事件；日志应按实验或线上容量合理控制。
java -Xlog:class+load=info,class+unload=info -jar app.jar
# 针对现有进程查看加载器相关统计，命令支持情况先查目标 JDK 帮助。
jcmd 12345 VM.classloader_stats
```

对比多次部署后的加载器数量、类数量与元空间曲线。只有增长现象还不能直接证明泄漏；应通过堆转储或诊断工具找到旧加载器的保留路径。

修复应落实到停止线程、移除 ThreadLocal、注销资源或缩短缓存生命周期。增大 `MaxMetaspaceSize` 只能延后失败，不能切断错误引用。

## 五、面试简答与追问

**简答：** 类卸载与定义加载器的可回收性相关。热部署泄漏往往是长寿命对象保留旧加载器，诊断要找引用链，而不是单纯调大元空间。

**追问：每次 Full GC 都一定卸载所有不用的类吗？** 不是。可达性、收集器支持、参数与实际回收过程共同决定是否卸载。

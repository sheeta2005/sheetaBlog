# 一个限流注解如何接入 Spring Boot

限流组件需要让业务方声明规则，也需要让“没有配置”和“明确配置”产生可预期的行为。我把接入链路分为三部分：启动时装配组件，调用时取得规则，执行前生成限流键。

调用顺序为 **Spring 代理 → 注解与全局规则合并 → SpEL 解析 → Redis 键 → Lua 判断 → 业务方法或异常**。

## Starter 负责引入，自动配置负责创建

项目包含父工程、自动配置模块与空 Starter。Starter 引入核心模块，Spring Boot 通过 `AutoConfiguration.imports` 发现自动配置。

配置类安排在 Redis 自动配置之后，要求存在 `StringRedisTemplate`，且组件没有被显式关闭。缺少 Redis 类、缺少模板或 `enabled=false` 时，不创建限流切面。业务方已经声明自定义切面时，默认配置也会退出。

启停是启动阶段的条件判断，改变配置后需要重新启动应用。当前没有运行时刷新能力，不能把它介绍成动态规则中心。

## 注解需要有“继承”的表达方式

如果注解的默认阈值直接设成 100，切面只要看见正数就使用注解，那么业务方即使什么都没写，也会覆盖全局配置。表面上支持三级优先级，实际上默认注解截断了继承路径。

当前实现将注解阈值和窗口默认设为 `-1`，算法默认为 `DEFAULT`：正数与明确算法覆盖全局配置，继承标记则沿用全局值，全局未配置时使用内置默认值。

| 情况 | 实际规则 |
| --- | --- |
| 注解显式指定阈值 50 | 使用 50 |
| 注解未指定，全局阈值 200 | 使用 200 |
| 两处都未指定 | 使用内置阈值 100 |
| 注解算法为 DEFAULT | 继承全局算法 |

全局阈值与窗口必须大于零，前缀不能为空，算法和故障策略也要有效。配置错误在初始化时失败，避免非法规则进入 Lua；它不属于 Redis 网络故障的降级范围。

## SpEL 让参数成为业务维度

切面使用方法实参与参数名建立表达式上下文。`#p0`、`#a0` 都代表第一个参数，也可以访问参数对象的属性。

按位置访问不依赖参数名；按名称访问需要业务项目保留相应编译信息。接口代理场景优先寻找实现类中的具体方法，再尝试接口方法，避免只读接口签名导致实现方法的参数名丢失。

生成维度时还要考虑业务命名空间。两个接口都返回同一个用户 ID，未必意味着它们应该共享额度；登录、验证码与其他操作通常需要各自的键前缀。

## 表达式失败后，规则会变粗

表达式为空、结果为 null 或解析失败时，当前实现记录日志并回退为类全限定名和方法名。调用仍有一个限流键，但原先按用户区分的规则可能变成整个方法共享。

因此表达式错误并非无影响的默认行为。默认键也不区分同名重载方法，需要区分时应明确声明业务键。

## 注解只拦截经过代理的调用

调用 Spring 管理的代理对象时，切面才有机会执行。手工创建对象、同一个对象内部通过 `this` 调用、私有方法或无法被代理的方法，都不能仅凭写了注解就认定限流生效。

测试应通过容器取得 Bean 并调用代理，还要覆盖接口代理、对象属性、注解覆盖与全局继承。只直接调用切面方法，会漏掉真实接入中的代理和自动装配问题。

# 用户态与内核态

## 一、为什么需要两种执行模式

普通程序不能任意修改页表、访问设备或读取其他进程的内存。操作系统把受保护的操作放在内核中，应用通过约定的接口请求服务。用户态与内核态描述的是 **CPU 执行权限**，不是两个独立进程。

Linux 中 Java 应用的大部分业务代码运行在用户态；文件读写、网络收发、线程创建等操作会涉及内核服务。系统调用前后的线程仍可以是同一条线程。

## 二、如何进入和退出内核

| 入口 | 触发原因 | 例子 |
| --- | --- | --- |
| 系统调用 | 程序主动请求受保护服务 | 读取文件、创建 socket |
| 异常 | 当前指令执行遇到问题 | 缺页、除零 |
| 硬件中断 | 外部设备或计时器通知 CPU | 网卡收包、时钟中断 |

以读取文件为例：应用准备参数，经系统调用入口进入内核；内核校验权限和地址，尝试从缓存或设备获取数据，最后返回结果。若必须等待设备，线程可能睡眠，调度器再安排其他可运行线程。

进入内核会保存必要的现场，返回时恢复。具体寄存器、入口指令与栈布局取决于架构，不能把某一种 CPU 的实现当成所有平台的规则。

## 三、模式切换与上下文切换

**模式切换** 改变执行权限；**上下文切换** 改变正在运行的任务。一次系统调用可以只发生模式切换，不切换线程。系统调用阻塞后，则可能同时引发调度和任务切换。

“每次进入内核都会复制整个进程内存”是错误说法。进程的地址空间继续存在，内核只保存恢复执行所需的状态；大量成本往往来自缓存失效、调度和等待。

## 四、后端开发中的关联

高频的小块 IO 可能增加系统调用次数，适当批量操作可以减少往返开销。但接口慢也可能是数据库等待或业务计算，不能看到线程很多就断言用户态与内核态切换过多。

排查时同时看用户 CPU、系统 CPU、上下文切换次数和请求耗时。`sys` 高只能提示内核工作较多，具体原因仍要结合调用栈与 IO 指标确认。

## 五、面试简答与追问

**简答：** 用户态限制应用权限，内核态允许操作受保护资源。系统调用、异常和中断是常见入口；权限切换不一定发生任务切换。

**追问：缺页是否一定读取磁盘？** 不一定。首次分配匿名页、写时复制等缺页可能只涉及内存；需要从文件或交换区读入页面时才会产生相关 IO。

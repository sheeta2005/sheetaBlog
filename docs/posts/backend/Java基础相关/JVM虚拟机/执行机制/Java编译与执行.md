# Java 编译与执行

## 一、从源码到运行

`javac` 将 Java 源码编译为 class 文件，其中包含字节码、常量池及其他类信息。JVM 加载类，完成验证、准备、必要的解析与初始化，然后执行方法。

class 文件不是当前 CPU 的机器码。字节码提供跨平台的中间表示，但操作系统功能、原生库与文件路径等仍可能影响应用的可移植性。

## 二、解释器与 JIT

| 环节 | 职责 | 代价与收益 |
| --- | --- | --- |
| 解释执行 | 按字节码语义逐步执行 | 启动较直接，长期热点性能受限 |
| JIT 编译 | 运行时把选中的方法或循环编译成机器码 | 消耗编译资源，改善热点性能 |
| 分层编译 | 结合不同编译级别与运行统计 | 平衡预热速度和最终优化 |

HotSpot 常见分层编译使用 C1 与 C2，但这是实现机制，不是 JVM 规范要求每个虚拟机必须这样做。热点判断会参考方法调用、循环回边等信息，不能固定背成“执行到同一个次数必定编译”。

## 三、运行时优化与去优化

JIT 可进行方法内联、逃逸分析和其他优化。它可能根据运行时观察做推测，例如某个调用目前只有一种实际接收者类型。

当新的类加载或执行路径使推测不成立时，JVM 需要去优化，回到安全的执行状态并可能重新编译。这不是业务异常，也不意味着之前的优化永远失效。

**OSR** 允许长时间运行的循环在方法尚未返回时切换到编译后的执行版本，与普通的方法入口编译需要区分。

## 四、观察工具与压测

```shell
# 查看 class 文件的字节码和元数据，不是查看最终 JIT 机器码。
javap -c -v Demo.class
# JDK 21 HotSpot：观察编译活动，实验时配合足够长的负载。
java -XX:+PrintCompilation -jar app.jar
```

压测应留出预热阶段，同时记录编译、GC 与业务指标。首次调用延迟不能直接代表稳态吞吐；手写一次短循环也容易受到常量折叠、死代码消除和计时误差影响。

## 五、面试简答与追问

**简答：** Java 通常先编译为字节码，再由 JVM 加载执行；HotSpot 结合解释与 JIT，把热点编译成机器码，并允许在推测失效时去优化。

**追问：Java 是解释型还是编译型？** 两种过程都存在，应分清源码编译、解释执行和运行时机器码编译，而不是用单一标签概括。

# HTTP 版本与连接复用

## 一、共同语义与不同传输

请求方法、状态码、资源和缓存等语义在不同 HTTP 版本中延续，变化主要体现在消息编码、连接使用和传输机制。升级 HTTP 版本不会自动改变接口的业务语义。

| 版本 | 消息与传输 | 连接特征 |
| --- | --- | --- |
| HTTP/1.1 | 通常基于 TCP，文本头部与消息定界规则 | 默认持久连接，可复用但响应有序 |
| HTTP/2 | 基于 TCP 的二进制帧，HPACK 压缩头部 | 一条连接中多条流并发 |
| HTTP/3 | 基于 QUIC，QPACK 压缩头部 | 独立流传输，集成 TLS 1.3 安全机制 |

HTTP/1.0 可通过扩展实现 keep-alive，因此不能说它任何情况下都只能短连接。HTTP/2 规范与浏览器实践也要区分，浏览器通常通过 TLS 和 ALPN 协商 HTTP/2。

## 二、多路复用解决哪种阻塞

HTTP/1.1 流水线中，后续响应不能越过先前响应，慢请求容易挡住后面请求。HTTP/2 用流标识交错发送帧，缓解这一应用层队头阻塞。

但 HTTP/2 仍共享一个 TCP 有序字节流。某段字节丢失后，TCP 必须补齐缺口才能继续交付后续字节，可能影响连接上的多个 HTTP/2 流。

## 三、HTTP/3 仍有哪些共同约束

QUIC 把可靠性和顺序保证放到各个流中，一个流的数据缺失不会直接要求其他流等待同一字节缺口。但多条流仍可能共享拥塞控制和网络带宽，QPACK 也需要处理头部依赖。

因此“HTTP/3 完全没有任何队头阻塞、一定更快”过于绝对。协议选择还受握手、网络条件、实现、服务器配置和 UDP 可达性影响。

## 四、缓存与幂等不能混淆

幂等描述相同请求重复执行的预期效果，例如 PUT；安全方法描述不预期修改服务端状态，例如 GET。可缓存性还取决于方法、响应状态和缓存指令，不能只看使用了哪个版本。

POST 不天然幂等，网络失败后的业务重试仍需应用约定。连接复用降低握手成本，但不等于数据库连接复用，也不意味着请求共享事务。

## 五、面试简答与追问

**简答：** HTTP/2 通过帧和流实现应用层多路复用，HTTP/3 借助 QUIC 降低跨流传输阻塞；HTTP 业务语义仍然需要单独正确设计。

**追问：HTTP/2 多路复用等于无限并发吗？** 不是。并发流数量、流量控制、服务器线程与下游容量都有边界。

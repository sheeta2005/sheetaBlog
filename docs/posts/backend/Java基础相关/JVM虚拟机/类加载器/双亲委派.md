# 双亲委派模型

## 一、父优先的标准流程

普通 ClassLoader 的默认加载思路是：先检查是否已加载，再让父加载器尝试，父找不到时才由当前加载器查找。没有父加载器时，会按实现委托引导加载器。

```text
loadClass(name)
  → findLoadedClass：当前加载器是否已有结果
  → 父加载器或引导加载器尝试
  → 若仍未找到，调用本地 findClass
  → 按请求需要处理解析并返回 Class
```

这是流程示意，实际实现还涉及加载锁与异常处理。父子关系主要是委派关系，不要求加载器类在 Java 继承结构上呈现同一层级。

## 二、JDK 版本差异

| 版本 | 典型内置层次 | 注意点 |
| --- | --- | --- |
| JDK 8 | Bootstrap → Extension → Application | 扩展目录与 rt.jar 属于旧布局 |
| JDK 9 及以后 | Bootstrap → Platform → Application | 使用模块化运行时，不能继续套 rt.jar |

引导加载器在常见 Java API 中以 `null` 表示，不代表该类根本没有加载来源。模块化类加载也存在更细的协作规则，父链不是全部运行时细节。

## 三、复用与类身份

父优先有助于复用父加载器提供的公共类型，避免子加载器各自定义不兼容的公共 API。但它 **不保证全 JVM 中某个类名只有一份 Class**。

类身份由 **二进制类名 + 定义类加载器** 共同确定。两个插件加载器分别定义同名类，可以得到不同类型，强制转换可能失败。

需要分清发起加载请求的加载器与真正定义类的加载器；委派成功后返回的类未必由最初调用者定义。

## 四、安全与自定义的边界

优先委派有助于维持核心类型的一致性，但 Java 核心包还受定义权限、模块等机制保护，不能只靠“父先找到了”解释所有安全限制。

自定义加载器通常重写 `findClass` 来保留父优先，只有确实需要隔离等需求时才设计特殊顺序。SPI 的线程上下文加载器帮助框架找到调用方提供的实现，也不能直接概括为每次都“彻底破坏双亲委派”。

Tomcat Webapp 默认有应用优先策略，同时保留核心和相关 API 的例外，见 [Tomcat 类加载机制](../../../Tomcat/Tomcat类加载机制)。

## 五、面试简答与追问

**简答：** 双亲委派通常先检查已加载，再向父委派，最后本地查找，有助于公共类型复用。类唯一性只在相应加载器身份范围内成立。

**追问：同名类为什么不能强转？** 先看定义加载器；名字相同、加载器不同，仍可能是不同类型。

**追问：JDK 21 还有 ExtClassLoader 吗？** 内置扩展加载器已由平台加载器替代，应结合模块化运行时说明，不能背 JDK 8 的目录流程。

# 进程间通信

## 一、为什么进程不能直接共享普通变量

进程通常具有独立虚拟地址空间。同一个数值地址在两个进程里可能映射到不同物理内存，因此把普通对象的指针传给另一个进程，不能自动共享对象。

IPC 的任务是提供可共同访问的通道或存储区域。**传递数据** 和**协调访问顺序** 是两件事，选定通信方式后仍可能需要同步机制。

## 二、常见方式对比

| 方式 | 特点 | 适用例子 |
| --- | --- | --- |
| 匿名管道 | 字节流，常用于有继承关系的进程 | Shell 命令流水线 |
| 命名管道 FIFO | 通过文件系统路径建立通道 | 本机简单数据交换 |
| 消息队列 | 按消息收发，保留消息边界 | 本机事件通知 |
| 共享内存 | 多进程映射同一片存储 | 大块数据低复制交换 |
| 信号 | 异步通知，承载数据能力有限 | 终止、重新加载通知 |
| Socket | 双向通信，支持本地或跨主机 | 服务调用、Unix 域套接字 |

匿名管道通常是单向的；需要双向交流时可建立两条管道。TCP Socket 是字节流，也不保留业务消息边界；应通过长度、分隔符或协议格式进行拆包。

## 三、共享内存为什么仍要加锁

假设两个进程共享一个计数器，读值、加一、写回不是一个不可分割操作。两个进程都读到 10，最后可能只写回 11，产生丢失更新。

需要使用支持进程间共享的互斥锁、信号量或恰当的原子协议来保护访问。只在各自进程里创建普通 Java 锁，无法协调另一进程。

共享内存减少了通过内核缓冲区反复搬运数据的需求，但创建映射、同步和缓存一致性仍有成本，不能笼统称为所有流程都“零开销”。

## 四、选型与故障处理

先看是否跨机器、数据量和频率，再看消息边界、背压和故障恢复。低频控制通知优先选择易维护的机制；大数据共享再考虑共享内存。

还要约定进程退出后如何释放资源、消费者过慢时是否阻塞或丢弃，以及部分写入如何识别。操作系统消息队列与 Redis、Kafka 等中间件不是同一层面的功能。

## 五、面试简答与追问

**简答：** IPC 通过管道、队列、共享内存、信号或 Socket 跨越进程隔离。共享内存适合大数据交换，但同步、协议和生命周期必须另行设计。

**追问：同一机器为什么还用 Socket？** 它提供成熟的双向协议与错误处理；Unix 域 Socket 还可避免跨网络传输，便于保留进程隔离。

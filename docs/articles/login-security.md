# JWT 之外：角色校验、数据归属与登录限频

takeMe 有老人、志愿者和管理员三类账号。接口收到有效 JWT，只能说明凭据通过了相应校验，还需要判断角色是否匹配、账号是否仍可用，以及当前操作的数据是否属于这个人。

登录入口又发生在 JWT 签发之前，需要单独限制重复请求，减少数据库查询和密码校验的压力。

## 身份、角色与归属分开检查

| 校验层次 | 要回答的问题 | 项目中的处理 |
| --- | --- | --- |
| 凭据 | 令牌是否有效，用户是谁 | JWT 解析与用户 ID 提取 |
| 角色 | 能否访问当前角色的接口 | 三类角色对应的拦截器 |
| 账号状态 | 账号是否已被停用或删除 | 查询数据库实时状态 |
| 资源归属 | 能否修改这个地址、订单或消息 | 服务端按当前身份限定记录 |

账号状态变化可能发生在令牌签发之后，所以不能只依赖令牌中的旧信息。当前 HTTP 请求与新建 WebSocket 连接都结合实时账号状态检查。

拦截器把身份写入请求上下文，结束后清理。头像等接口使用当前登录 ID，地址操作和消息已读更新同时带上资源 ID 与归属条件。客户端传来的 ID 不应替代服务端已经确认的身份。

## 登录先按账号限制，再用 IP 辅助

社区用户可能共用一个出口 IP。只按 IP 设置很小的配额，会让不同老人的正常登录相互影响；只按账号限制，又不足以覆盖一个来源反复尝试不同账号的行为。

当前登录切面从登录参数取得账号标识作为主要限流维度，另加较宽松的 IP 配额。老人登录接口当前声明每账号 60 秒最多 10 次，辅助 IP 默认配额更宽，用于额外约束来源请求。

这种配额设计解决的是请求频率问题，不能单独证明已经阻止全部撞库或自动化攻击。账号名变化、共享出口、可信代理配置，都需要结合实际部署判断。

## Lua 把计数和首次过期放在一起

如果应用分别执行计数与过期设置，中途失败可能留下没有有效过期时间的计数键，并发请求也会使判断复杂化。

takeMe 的 Lua 在 Redis 内执行计数，首次请求设置 TTL，再返回是否超过阈值。切面在调用登录业务前检查结果，超限时直接返回业务错误，减少后续查询和 BCrypt 校验的执行。

这里的窗口从首次计数开始，到 TTL 到期结束。它与独立 Starter 中使用 Redis 时间划分的对齐固定窗口实现不同；takeMe 当前使用自己的 `redis-starter`，没有把独立 Starter 的测试结果直接用于此登录入口。

## IP 与错误码都有边界

当前来源 IP 读取 `remoteAddr`，没有直接相信客户端自行提交的转发头。部署反向代理后，需要由应用结合可信代理规则决定真实 IP 的取得方式。

超限返回对象包含业务错误码 429。业务结果码与 HTTP 状态是两个层次，不能只看到返回对象就认定接口已经发送 HTTP 429；需要结合控制器及异常处理的实际响应核对。

Redis 关闭时当前限流会退出或放行，这与数据库中的账号状态校验不同。关闭中间件意味着相应频率保护不再生效，不能将配置关闭后的正常响应当作限流验证通过。

## 退出与停用不是同一件事

当前退出依赖前端删除 JWT、断开连接，项目没有全局 JWT 撤销列表。有效期内的令牌是否还能使用，需要结合账号状态和令牌有效性判断，不能因为调用退出接口就宣称旧凭据已经全局失效。

复核认证时应分别覆盖跨角色访问、停用账号、他人数据、重复登录和共享 IP；这些测试检验不同的保护层，不能用一次正常登录代替。

# 服务目录缓存：把空值、失效和并发回源一起考虑

takeMe 的老人端需要按类型展示上架服务，管理端需要查看订单、审批和趋势统计。这些查询会重复出现，适合缓存；订单状态和权限判断则继续以数据库记录为准。

给查询加缓存之后，还需要回答三个问题：查不到数据是否也缓存，套餐变更后什么时候失效，以及热点键过期时有多少线程会同时查询数据库。

## 先确定缓存的职责

| 数据 | 缓存方式 | 需要关注的变化 |
| --- | --- | --- |
| 按类型查询的上架目录 | 以类型区分查询键 | 新增、类型修改、下架与删除 |
| 管理端聚合看板 | 缓存可重建的统计结果 | 缓存时效与统计口径 |
| 查询返回 null | 使用短期空值哨兵 | 区分缓存未命中和已经查过的空值 |
| 查询返回空列表 | 作为正常结果缓存 | 空列表与 null 的业务语义不同 |

目录类型先做合法性校验，避免陌生参数无限制造查询和缓存键。缓存键由业务前缀及指定方法参数组成，参数选择需要与查询结果的变化维度一致。

## 缓存未命中后再检查一次

当前部署是单 JVM，热点回源采用固定的 64 条锁条带。业务键映射到其中一把锁，避免为每个陌生键长期创建一个锁对象。

处理顺序为：**读取缓存 → 获取对应锁 → 再读缓存 → 查询数据库 → 写入缓存**。

第二次读取很关键。后到的线程可能已经等过一次锁，此时第一个线程已经写好结果；如果不复查，等待者仍会逐个查询数据库，锁只会把并发回源变成排队回源。

不同键可能落到同一条锁带，带来少量额外串行，这是固定内存占用与并发程度之间的取舍。这套锁只能协调当前进程，不能合并另一台应用服务器的查询。

## 主动失效也要与回源协调

套餐新增、修改类型、下架和删除会使对应目录缓存过时。有外层事务时，失效操作安排在事务提交后，避免数据库还没提交就让其他请求重建旧数据。

还有一种更隐蔽的竞争：查询先读到旧目录，套餐修改随后提交并删除缓存，旧查询最后才把结果写入缓存。仅仅“修改后删除”无法覆盖这一窗口。

当前回源和主动失效使用同一套本机锁协调，减少旧查询在失效完成后重新写回旧目录的机会。数据库提交与 Redis 删除仍属于不同系统，删除失败、进程退出和多 JVM 场景需要另外处理，不能把本机锁说成完整的分布式缓存一致性方案。

## TTL 抖动与异常分别处理

缓存时长增加约 ±10% 的随机偏移，减少一批键同时到期。空值也有过期时间，使后续新出现的数据有机会被重新查询。TTL 抖动分散失效时间，热点键的并发回源仍靠前面的锁与复查处理。

读取或写入查询缓存出现 Redis 访问、序列化异常时，当前逻辑允许查询回源并保留数据库结果。数据库业务异常继续向上传播。限流计数承担不同职责，不能直接套用查询缓存的降级处理。

## 已有验证说明了什么

专项记录中，冷看板同时发起 20 个真实 HTTP 请求，全部成功，代理调用为 20 次，实际业务回源为 1 次。这个结果支持当时单 JVM 下的回源合并行为。

还需要检查套餐变更后目录是否更新、空列表是否被重复查询、null 哨兵是否到期，以及缓存异常后数据库错误是否被错误吞掉。一次冷缓存测试不能推导 Redis 全实例故障时的数据库容量，也不能证明多实例间的缓存一致性。
